# Firmware V2.8 Planning Notes

Dokumen ini adalah checkpoint perencanaan Firmware V2.8. Isi dokumen ini belum
otomatis berarti sudah diimplementasikan. Setiap bagian menandai status saat ini
dan target perubahan berikutnya.

## 1. Status Schedule Saat Ini

Sudah diimplementasikan:

- Master selalu subscribe ke `HD01/control/schedule`.
- Payload `PRE_CLASS_ON` langsung menyalakan AC dan lampu serta membatalkan
  shutdown timer yang masih aktif.
- Payload `CLASS_ENDED` memulai shutdown timer 20 menit.
- Setelah timer habis, AC dan lampu dimatikan jika ruangan terkonfirmasi kosong.
- Jika ruangan masih terisi atau status presence belum valid, master menunggu
  dan melakukan pemeriksaan ulang setiap 5 menit.

Belum diimplementasikan:

- Parsing payload jadwal harian `YYYYMMDD;HHMM-HHMM;...`.
- Overwrite dan penyimpanan jadwal harian ke NVS.
- Trigger lokal otomatis pada `start - 20 menit` dan `end`.
- Catch-up setelah master reboot di tengah jadwal kelas.

Target V2.8 adalah menyelesaikan schedule engine lokal tersebut sehingga server
cukup mengirim jadwal lengkap sekali sekitar tengah malam.

## 2. Rekomendasi Polling RS485 dan Publish MQTT

Polling RS485 dan publish MQTT SHALL dipisahkan. Master dapat membaca sensor
secara cukup sering untuk safety dan kontrol lokal tanpa harus mengirim setiap
pembacaan ke MQTT.

| Data | Poll RS485 normal | Publish MQTT normal | Mode cepat / event |
|---|---:|---:|---|
| Temperature | 30 detik | 5 menit | Setelah AC pertama ON atau target berubah signifikan: poll dan publish setiap 5 detik selama 5 menit, lalu kembali normal. |
| CO2 | 30-60 detik | 5 menit | Publish segera jika melewati threshold bahaya atau berubah signifikan. |
| Human presence | 5-15 detik | Saat berubah + heartbeat 5 menit | Tetap cepat karena dipakai untuk occupancy safety dan smart shutdown. |
| Room Lux | 30-60 detik | 5 menit | Setelah lampu ON/OFF, tunggu 5 detik lalu poll dan publish segera. |
| Projector verification Lux | 1-2 detik selama verifikasi | Tidak dipublish sebagai room Lux | Dipakai internal selama projector powering/retry/verification. |
| LED state | Setelah command/poll konfirmasi | Saat berubah + heartbeat 5 menit | Publish segera setelah state berubah. |
| AC state | Setelah command/poll konfirmasi | Saat berubah + heartbeat 5 menit | Temperature burst mode aktif setelah AC ON. |

Catatan:

- Human presence tidak boleh dipoll hanya setiap 5 menit karena dapat membuat
  safety override dan shutdown terlambat.
- Heartbeat 5 menit menjaga server tetap memiliki state terbaru tanpa membebani
  MQTT secara berlebihan.
- Event penting tetap dipublish segera; interval 5 menit hanya berlaku ketika
  state stabil.

## 3. Pembagian Fungsi Lux

Lux SHALL dipisahkan secara logis menjadi tiga fungsi:

1. **Projector verification Lux**
   - Menggunakan perubahan per-channel terhadap baseline masing-masing.
   - Tidak masuk ke nilai `HD01/data/lux`.
   - Minimal satu channel yang naik dapat membuktikan projector kemungkinan ON.
   - Channel lain yang invalid atau tidak berubah menghasilkan status
     `CHECK_LUX`, bukan mematikan projector.

2. **Room Lux**
   - Dipakai dashboard dan `HD01/data/lux`.
   - Menggunakan median dari channel room Lux yang sehat, bukan average seluruh
     Lux termasuk projector verification Lux.
   - Dipublish 5 detik setelah lampu berubah, lalu heartbeat setiap 5 menit.

3. **Lux sensor anomaly**
   - Membandingkan normalized value setiap channel terhadap baseline masing-masing.
   - Minimal 3 room Lux valid direkomendasikan untuk mendeteksi satu outlier.
   - Warning hanya muncul jika penyimpangan lebih dari sekitar 40% dan bertahan
     selama 5 pembacaan ketika lampu/projector tidak sedang transisi.
   - Channel suspect tidak langsung dihapus; room Lux memakai median channel
     sehat sampai channel tersebut kembali normal.

## 4. Gabungan Lux dan Active-Load Anomaly

Average 5-7 hari yang sudah ada adalah average durasi active load:

```text
active_load = light_on || ac_on
```

Itu bukan average nilai Lux. V2.8 SHALL mempertahankan active-load history dan
menggunakan Lux sebagai bukti tambahan.

Contoh interpretasi:

| Relay / state | Lux response | Interpretasi |
|---|---|---|
| Lamp ON | Room Lux naik | Lampu kemungkinan benar-benar menyala. |
| Lamp ON | Room Lux tidak naik | Warning check lamp atau check Lux. |
| Lamp OFF | Room Lux tetap tinggi | Kemungkinan cahaya luar atau projector. |
| Satu room Lux terus menyimpang | Channel Lux suspect. |
| Empty + after-hours + active load abnormal + lamp verified ON | Active-load anomaly dengan keyakinan tinggi. |

Alert Bit 7 tetap berarti after-hours empty-room active-load anomaly. Warning
Lux outlier/check lamp membutuhkan status warning terpisah atau bit baru agar
tidak tercampur dengan Bit 2 yang berarti Lux invalid.

## 5. Server Override dan Occupancy Safety

Master tetap menjadi authority terakhir untuk lampu ketika presence terdeteksi.

Rules:

- Jika `human_presence_valid == true` dan `human_presence == true`, semua command
  lampu dari server/MQTT SHALL ditolak. Server tidak boleh menyalakan maupun
  mematikan lampu dan mengoverride master.
- Jika `human_presence_valid == true` dan `human_presence == false`, command
  lampu dari server SHALL langsung diterima, termasuk command OFF.
- Jika presence belum valid/unknown, target safety policy saat ini tetap
  konservatif untuk lampu OFF sampai keputusan final dibuat.
- Local HMI tetap dapat mengontrol lampu sebagai override pengguna di ruangan.
